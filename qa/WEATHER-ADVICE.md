# 天气问答扩展验收与取舍

执行日期：2026-11-17（Asia/Shanghai）。范围：[天气问答规格](../docs/specs/2026-11-17-weather-advice.md) AC1–AC4。直接复现用户截图中的“今天广州天气怎样 → 出门穿什么衣服”，扩充共享服务端与 Web 展示；本轮不涉及 Flutter SSE 或原生安装包。

## 当前支持范围

| 新增／增强问题 | 回答内容 |
| --- | --- |
| 今天广州天气怎样？ | 当地日期、温度范围和天气现象，附当天依据 |
| 出门穿什么衣服？要带外套吗？ | 指定时段温度、降水与天气现象，给出穿衣／分层／雨具建议 |
| 适合跑步、骑行、登山或出游吗？ | 依据温度、降水概率和雷雨／较强雨雪判断一般户外安排，不把它当作空气质量、路况或个人体能评估 |
| 可以晾衣服吗？ | 有雨雪或较高降水概率时建议室内；条件允许时可考虑室外，但不估算缺少湿度、风速依据的晾干速度 |
| 需要防晒吗？紫外线强吗？ | 清楚说明当前缺少紫外线指数，只给一般白天外出准备建议，不虚构指数、等级或 SPF 数值 |
| 会下雪、起雾或有雷雨吗？现在是什么天气？ | 汇总时段天气现象，明确预报是否显示降雪／雷雨；未知天气码不当作“没有”。当前现象支持当前读数依据 |

原有温度、降雨／带伞、最暖／最冷、散步时段、每日预报及两城温度／降水比较保留。四语支持同一套服务端计算。直接问风速、湿度、空气质量、降水总量或历史天气仍提示当前没有相应数据。

## 五分钟复现

从首尔深链打开“问天气”，依次发送“今天广州天气怎样”“出门穿什么衣服”“明天呢”“那下午呢”“适合跑步吗”“需要防晒吗”“可以晾衣服吗”“会下雪吗”。确认回答一直是广州，日期由今天变成明天，时段随后保留下午 12–17 点；每条小时依据打开广州 `Asia/Shanghai` 的对应日期、时段和天气现象。

真实生产联验中，广州今天逐日预报为 21.1–28.2°C、毛毛雨；穿衣问题使用当地剩余小时 14–23 点，范围 22.5–28°C、最高降水概率 54%，返回轻薄透气衣物及雨具建议。每日概述与剩余小时的温度范围口径不同，回答明确标明各自日期／时段。[正式服务结果](evidence/weather-advice-production.json)、[截图](evidence/weather-advice-production-zh-Hans.png)。

## 实现位置

- `web/lib/weather-advice.ts`：五个新增意图 `clothing`、`outdoor`、`laundry`、`sun`、`conditions`，四语计算文案与对应小时证据；分类、事实与建议在服务端完成。
- `web/lib/ask.ts`：规则及模型计划支持新意图；每日预报附天气现象，当前现象可用 `now` 窗口，其他建议使用明确小时范围。模型继续只提取 JSON 计划，不生成天气读数或建议正文。
- `web/lib/types.ts`、`contracts.ts`：新增意图与合法窗口校验；JSON、SSE 及浏览器结构化结果使用同一契约。
- `web/lib/single-city.ts`：保留目的地日期与时段，从每日预报转到生活建议时继承原日期；规则城市解析排除通用提问词。支持 `city, region, country` 的明确消歧，按原始上游地区和国家字段匹配，仍对未消歧的同名城市报错。
- `web/components/AskDialog.tsx`：小时依据和城市预览展示天气现象，图标位于文字末尾；保留逐字显示、停止、历史和四语错误处理。

## 过程与取舍

1. **扩充现有数据能支撑的能力。** 继续使用温度、降水概率和 WMO 天气码，没有扩大天气上游字段或接入新数据源；旧快照、原生 JSON 与共享缓存格式兼容。防晒回答明确缺少 UV 指数，晾衣回答明确缺少湿度、风速，避免从温度或晴天推出这些指标。
2. **事实与建议分开。** 先显示对应小时的温度范围、天气现象及降水概率，再显示建议；证据包括温度低／高点、降水峰值及不同天气现象的代表小时，均含目标城市、版本和时区。缺失降水不是 0%，缺测时不肯定推荐室外活动／晾衣。
3. **建议采用明确的产品规则。** 穿衣按最低温度 `<5`、`<15`、`<22`、其余分档，温差至少 8°C 时补充分层；这属于一般舒适度提示，没有宣称适合所有人的服装标准。户外判断优先考虑雷雨／较强雨雪，其次降水和高低温；没有把“适合跑步”写成个人运动安全保证。
4. **日期继承使用目的地日历。** 从每日概述切到穿衣时，保持原日期，用当地 0–23 点范围；当天只采用仍可用的剩余小时，答案打印实际选用范围。追问“明天”“下午”分别改变日期与时段，后续跑步／防晒／晾衣继续保留两者。
5. **保留并修复实际失败。** 首轮规则测试发现“晾衣服”中的“衣服”抢先命中穿衣，调整为晾衣优先；实际浏览器随后发现“需要防晒吗”将“需要”误当城市，增加通用词排除并补入连续追问测试。修复后对应路径均通过。
6. **同名城市不猜测。** 英文 Guangzhou 实际返回广东和江西的同名地点，首次英文联验因此正确报歧义。补上逗号分隔的地区／国家过滤后，使用明确的 `Guangzhou, Guangdong, China` 重测通过；未明确地区的歧义仍保留。地区／国家目前按地名服务返回的文字匹配，不做跨语言模糊推断。韩文 광저우 通过原始上游搜索并匹配相应城市，不硬编码广州坐标。
7. **控制回归范围。** 新增业务数据仍由同一 `/api/ask` 服务端计算，未调整模型供应商、SSE 协议和逐字播放逻辑。Flutter 可继续调用共享 JSON 接口，但本轮没有声称完成 Flutter 对话历史、单城上下文或 SSE 界面的同步升级。
